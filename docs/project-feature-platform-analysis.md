# winSwitch 项目功能与平台限制分析

## 1. 项目定位

`winSwitch` 是一个基于 Qt 6 的跨平台桌面窗口切换管理器，目标是在 Windows、macOS、Linux 上提供统一的窗口切换体验。

当前项目的核心使用路径是：

1. 程序启动后常驻系统托盘
2. 用户通过全局快捷键或托盘入口打开切换面板
3. 程序枚举当前系统中的窗口并按应用分组
4. 用户通过鼠标或键盘快速激活、关闭、筛选窗口
5. 程序根据配置保存置顶应用、排除应用、语言和面板选项

从当前代码实现看，Windows 版本已经接近完整可用；macOS 和 Linux 版本仍处于基础支持或平台适配补齐阶段。

## 2. 当前已实现的主要功能

### 2.1 托盘常驻

- 程序启动后驻留托盘
- 托盘菜单支持打开设置和退出
- 双击托盘图标可打开切换面板

### 2.2 单实例运行

- 通过共享内存保证程序只运行一个实例
- 重复启动时会提示程序已在运行

### 2.3 窗口采集与分组

- 从各平台获取当前系统窗口列表
- 按应用程序分组展示窗口
- 支持排除指定应用
- 支持将指定应用置顶显示
- 对资源管理器类窗口做额外处理

### 2.4 切换面板

- 展示应用分组和窗口卡片
- 支持点击卡片激活窗口
- 支持关闭单个窗口
- 支持关闭整个应用组的窗口
- 支持按应用筛选视图
- 支持键盘导航

### 2.5 纹理展示

- 支持窗口缩略图
- 支持窗口图标
- 图标和缩略图采用分批异步加载，减少面板首次显示时的卡顿

### 2.6 设置能力

- 支持修改全局快捷键
- 支持开关缩略图显示
- 支持切换界面语言
- 支持配置排除应用列表
- 支持配置置顶应用列表

## 3. 当前功能边界

虽然核心链路已成型，但目前仍有一些明显边界：

- 只有按应用分组过滤，没有按标题或关键字实时搜索
- 没有最近使用顺序排序
- 没有多屏幕感知，面板默认居中到主屏幕
- 没有最小化、恢复、移动到桌面等更多窗口操作
- 热键录入支持的按键种类较少
- 不同平台在热键、图标、缩略图和关闭能力上差异明显

## 5. 各系统限制分析

### 5.1 Windows

Windows 是当前支持最完整的平台。

已具备能力：

- 全局热键注册
- 窗口枚举
- 窗口激活
- 关闭窗口
- 关闭应用组
- 图标抓取
- 缩略图抓取
- Explorer 路径识别和排序

当前限制：

- 缩略图依赖 `PrintWindow`，某些特殊窗口、受保护窗口、硬件加速窗口可能无法稳定抓取
- 热键系统支持的键位种类仍不够丰富
- 某些系统级窗口、工具窗口、隐藏窗口会被主动过滤

总体结论：

- Windows 端已达到主力使用水平
- 后续重点主要是体验增强，而不是基础能力补齐

### 5.2 macOS

macOS 当前属于基础支持阶段。

已具备能力：

- 枚举屏幕上的普通窗口
- 按应用分组展示
- 基于应用前台激活窗口所属应用
- 部分情况下获取窗口缩略图

当前缺失：

- 全局热键未真正实现
- 关闭单窗口和关闭整组窗口未实现
- 窗口图标未实现
- 激活更偏向“激活应用”，不是严格聚焦某个具体窗口
- Finder 目录信息只是用窗口标题近似表示，不是真实路径

当前限制：

- macOS 对跨应用窗口控制天然更保守
- 需要依赖 Accessibility API、AppleScript 或系统权限才能做更深层窗口操作
- 新版系统对窗口截图和窗口内容采集可能更严格

总体结论：

- 目前更适合作为窗口浏览器和基础切换器
- 要达到 Windows 级体验，必须补齐热键、关闭窗口、精确窗口激活和权限适配

### 5.3 Linux X11

Linux X11 当前属于“基础可跑，但不完整”的阶段。

已具备能力：

- 通过 EWMH 协议获取窗口列表
- 激活窗口
- 请求关闭窗口
- 使用 `XGetImage` 获取窗口缩略图

当前缺失：

- 全局热键未实现
- 窗口图标未实现
- 文件管理器路径增强未实现

当前限制：

- 功能依赖窗口管理器和桌面环境是否遵循 EWMH 规范
- `XGetImage` 在某些 compositor 或窗口类型下可能失败
- 不同发行版、窗口管理器之间兼容性差异大

总体结论：

- Linux X11 还不能算完整可用版本
- 若补齐热键并增强兼容性，能够成为一个可用的桌面工具

### 5.4 Linux Wayland

Wayland 是当前限制最强的平台环境。

当前状态：

- 代码中检测到纯 Wayland 会直接返回空窗口列表或空结果
- 激活窗口、关闭窗口、缩略图采集、全局热键基本都不可用

原因：

- Wayland 从设计上限制客户端直接观察和操控其他应用窗口
- 普通应用通常拿不到全局窗口列表
- 普通应用通常不能自由注册跨桌面全局热键
- 普通应用通常不能直接读取其他窗口像素内容

总体结论：

- Wayland 下不是“当前代码没做完”，而是“平台设计本身就强限制”
- 后续即使扩展，也只能依赖 portal、桌面环境扩展、系统服务或文档化降级方案

## 6. 可以扩展增加的功能

以下功能是当前项目最值得考虑的扩展方向。

### 6.1 搜索与筛选增强

- 增加关键字搜索框
- 支持按窗口标题搜索
- 支持按应用名搜索
- 支持按路径搜索
- 支持搜索结果高亮
- 支持拼音匹配和首字母匹配

价值：

- 这是最直接提升效率的功能
- 也是当前界面能力中最明显的缺口

### 6.2 排序能力增强

- 增加最近使用顺序排序
- 增加按应用名排序
- 增加按窗口数排序
- 增加按置顶优先加最近使用的混合排序

价值：

- 能显著提升实际切换效率
- 更接近用户对 Alt+Tab 类工具的使用习惯

### 6.3 更多窗口操作

- 最小化窗口
- 恢复窗口
- 关闭其他窗口
- 最小化同组其他窗口
- 打开应用所在目录
- 对文件管理器窗口执行“定位当前路径”

价值：

- 能把项目从“切换器”增强为“窗口管理器”

### 6.4 多屏支持

- 面板显示在鼠标所在屏幕
- 面板显示在当前前台窗口所在屏幕
- 记忆上次显示屏幕
- 不同屏幕支持不同尺寸策略

价值：

- 多显示器场景下体验提升非常明显

### 6.5 热键系统增强

- 支持更多主键和组合键
- 增加冲突检测
- 增加热键不可用时的更明确提示
- 支持平台差异化热键建议

价值：

- 可以显著改善可配置性和稳定性

### 6.6 界面与体验增强

- 深色模式和浅色模式切换
- 毛玻璃或半透明效果
- 紧凑模式与大卡片模式
- 操作确认弹窗
- 动画过渡效果
- 首次使用引导页

### 6.7 配置与运维增强

- 开机自启动
- 导入导出配置
- 配置备份与恢复
- 日志查看页
- 平台能力诊断页
- 权限状态提示页

## 7. 哪些功能受平台限制，难以统一实现

下面这些功能不是单纯“多写代码就行”，而是会被系统模型、权限模型或桌面协议本身限制。

### 7.1 在所有平台上统一实现“精确控制任意第三方窗口”

原因：

- Windows 对外部窗口控制最开放
- macOS 需要额外权限，且很多能力依赖辅助功能接口
- Linux X11 能做一部分，但不同窗口管理器兼容性不一致
- Wayland 默认不允许应用自由控制其他应用窗口

影响：

- 无法保证所有平台都能稳定做到“指定窗口激活、关闭、最小化、恢复、移动、置顶”

### 7.2 在所有平台上统一获取完整全局窗口列表

原因：

- Windows 和 X11 较容易实现
- macOS 能获取部分可见窗口信息，但受系统和权限影响
- Wayland 默认不向普通应用公开完整窗口列表

影响：

- “跨平台统一窗口枚举”在 Wayland 下通常无法成立

### 7.3 在所有平台上统一实现全局热键

原因：

- Windows 原生支持较好
- macOS 需要专门系统接口和权限配合
- X11 可实现但兼容性一般
- Wayland 多数环境默认禁止普通应用注册通用全局热键

影响：

- 全局热键无法成为所有系统下都可靠一致的能力

### 7.4 在所有平台上统一抓取任意窗口缩略图

原因：

- Windows 可通过系统 API 抓取，但仍有特殊窗口例外
- macOS 对截图和跨应用窗口内容获取更敏感
- Linux X11 依赖底层图像抓取，兼容性一般
- Wayland 默认禁止读取其他应用窗口内容

影响：

- “统一实时缩略图”无法保证跨平台稳定可用

### 7.5 在所有平台上统一读取文件管理器窗口真实路径

原因：

- Windows Explorer 可以通过 COM 获取
- macOS Finder 和 Linux 文件管理器没有统一稳定的跨应用公开接口
- 不同文件管理器实现差异很大

影响：

- 只能对特定平台、特定文件管理器做专项适配
- 无法作为普适跨平台能力承诺

### 7.6 在所有平台上统一实现“关闭应用组全部窗口”

原因：

- Windows 可以逐个发送关闭消息
- X11 可以尝试发送删除窗口协议
- macOS 没有统一跨应用窗口关闭语义
- Wayland 更不允许普通应用做类似操作

影响：

- 关闭整组窗口更适合定义为“平台能力支持项”，而不是无条件可用功能

### 7.7 在所有平台上统一实现窗口图标获取

原因：

- 不同系统对“窗口图标”的定义并不一致
- 有的平台更容易拿到应用图标，而不是窗口图标
- Linux 和 macOS 上常常需要退化为应用图标、桌面条目图标或 bundle 图标

影响：

- 图标能力通常只能做到“尽量显示”，很难保证完全统一

## 8. 从产品角度建议如何处理平台限制

与其追求所有平台完全一致，更现实的方案是“核心体验统一，能力按平台降级”。

建议策略：

### 8.1 定义分层能力

- 核心层：托盘、面板、分组、搜索、设置
- 平台增强层：热键、关闭窗口、缩略图、图标、路径解析
- 高限制平台降级层：只展示窗口列表和基础切换

### 8.2 在界面中明确提示平台差异

- 在设置页展示当前平台支持的能力
- 对不可用功能直接禁用并给出原因
- 对需要权限的功能提示用户授权

### 8.3 对 Wayland 采取明确降级策略

- 明确说明 Wayland 的限制来源于平台安全模型
- 如果没有 portal 或桌面扩展支持，则只提供有限功能
- 避免对 Wayland 承诺与 Windows 一样的体验

### 8.4 优先投入最有收益的扩展

建议优先级：

1. 搜索能力
2. 最近使用排序
3. 多屏支持
4. Windows 体验增强
5. macOS 热键与关闭能力
6. Linux X11 热键
7. 平台能力提示与诊断页

## 9. 结论

当前项目的真实状态可以概括为：

- Windows 版本最完整，已经具备较强实用性
- macOS 版本能做基础浏览和切换，但关键能力缺失较多
- Linux X11 版本有基础能力，但仍未形成完整使用闭环
- Linux Wayland 受平台模型限制，很多能力无法作为普通桌面应用直接实现

如果后续继续推进，最值得投入的方向是：

- 搜索与筛选增强
- 最近使用排序
- 多屏支持
- macOS 热键和关闭能力补齐
- Linux X11 热键补齐
- 平台能力探测、权限提示和降级说明

从长期看，这个项目更适合定位为：

- 在 Windows 上提供完整体验
- 在 macOS 和 Linux 上提供分阶段增强体验
- 在 Wayland 上提供明确降级和限制说明
