# mySwitcher 开发路线图

## 1. 路线图目标

这份路线图用于把 `mySwitcher` 的后续工作拆解为更容易执行的阶段版本。

设计原则：

- 先增强主流程体验，再补齐平台能力缺口
- 先做低风险高收益功能，再推进高风险平台特性
- 对受平台限制的能力采用分级支持和降级策略

当前版本状态可概括为：

- Windows：接近完整可用
- macOS：基础支持
- Linux X11：基础支持但主入口不完整
- Linux Wayland：受平台机制限制，仅适合降级支持

## 2. 产品阶段目标

### 2.1 v0.2 目标

把产品从“能工作”提升到“更好用”，优先强化所有平台都能共享的主流程体验。

### 2.2 v0.3 目标

补齐 macOS 和 Linux X11 的关键缺口，让跨平台版本真正形成基础可用闭环。

### 2.3 v1.0 目标

形成稳定、可发布、可维护的跨平台窗口切换工具，并明确不同平台的能力边界和降级策略。

## 3. v0.2 规划

### 3.1 版本主题

`体验增强版`

### 3.2 版本目标

- 提升窗口定位和切换效率
- 提升多屏使用体验
- 提升热键配置和问题可解释性
- 减少“功能有了但不够顺手”的使用阻力

### 3.3 建议纳入范围

#### 核心功能

1. 面板关键字搜索
2. 最近使用排序
3. 多屏幕感知显示
4. 热键录入能力增强
5. 热键冲突和失败提示增强

#### 体验和配置功能

1. 平台能力诊断页
2. 导入导出配置
3. 更清晰的首次使用提示
4. 更明确的不可用能力提示

### 3.4 预期成果

- 打开面板后能快速搜索到目标窗口
- 列表排序更符合实际使用习惯
- 多屏场景下不再总是跳到主屏幕
- 用户可以更容易理解“为什么某个功能不可用”

### 3.5 技术拆分建议

#### 搜索能力

- 在面板增加搜索输入框
- 在模型层增加按标题、应用名、路径过滤
- 增加搜索高亮
- 允许后续扩展拼音匹配

#### 最近使用排序

- 在窗口激活后记录窗口或应用的最近使用时间
- 增加新的排序策略
- 在设置页允许用户选择排序模式

#### 多屏支持

- 获取鼠标所在屏幕
- 获取前台窗口所在屏幕
- 支持按策略显示面板

#### 诊断页

- 展示当前平台
- 展示 X11/Wayland 状态
- 展示热键状态
- 展示缩略图和图标能力状态
- 展示日志路径

### 3.6 风险点

- 搜索与现有分组模型如何协同，需要定义清晰交互
- MRU 与置顶排序可能冲突，需要明确排序优先级
- 多屏策略要避免在不同系统上表现不一致

### 3.7 验收标准

- 用户可通过搜索快速定位窗口
- 面板可根据屏幕策略显示在合理位置
- 最近使用排序可稳定工作
- 热键配置失败时给出明确原因
- 诊断页能直观看出当前平台支持能力

## 4. v0.3 规划

### 4.1 版本主题

`跨平台闭环版`

### 4.2 版本目标

- 补齐 macOS 的主要可用性缺口
- 补齐 Linux X11 的主入口能力
- 强化不同平台上的降级和说明策略

### 4.3 建议纳入范围

#### macOS 方向

1. 全局热键实现
2. 关闭窗口能力实现
3. 更明确的权限检查和提示
4. 尽可能改进窗口激活精度

#### Linux X11 方向

1. 全局热键实现
2. 图标获取能力增强
3. 兼容性测试与问题规避

#### 通用方向

1. 更多窗口操作入口
2. 日志与问题诊断增强
3. 不同平台功能矩阵在 UI 中可视化

### 4.4 预期成果

- macOS 至少具备“可唤出、可浏览、可切换、可关闭”的基础闭环
- Linux X11 至少具备“可唤出、可浏览、可切换”的主流程闭环
- 用户能在界面中明确知道平台支持哪些功能

### 4.5 技术拆分建议

#### macOS

- 评估 Carbon HotKey 或替代方案
- 引入 Accessibility API 能力检测
- 为关闭窗口失败设计提示和降级策略
- 区分“激活应用”和“聚焦窗口”的语义

#### Linux X11

- 实现热键注册逻辑
- 补充失败重试和错误提示
- 测试 GNOME X11、KDE X11 等常见环境

#### 通用

- 扩展平台能力探测接口
- 在设置页或诊断页显示功能可用性

### 4.6 风险点

- macOS 权限相关能力受系统版本和用户授权影响大
- Linux X11 兼容性在不同发行版之间可能差异明显
- 图标和窗口控制接口在平台间很难做到完全一致

### 4.7 验收标准

- macOS 可通过热键唤出面板
- macOS 可尝试关闭目标窗口并给出失败反馈
- Linux X11 可通过热键唤出面板
- 诊断页能正确反映平台差异和限制

## 5. v1.0 规划

### 5.1 版本主题

`稳定发布版`

### 5.2 版本目标

- 形成稳定可靠的核心体验
- 明确平台差异和产品边界
- 达到可以长期维护和对外发布的状态

### 5.3 建议纳入范围

#### 稳定性与产品化

1. 补齐自动化测试或关键回归检查
2. 优化异常日志和错误提示
3. 完善发布说明和平台限制说明
4. 完善首次使用引导

#### 产品能力

1. 更多窗口操作
2. 主题与界面增强
3. 开机自启动
4. 更完整的设置项管理

#### 平台策略

1. Windows 继续做完整体验标杆
2. macOS 明确权限依赖和降级说明
3. Linux X11 明确支持范围
4. Wayland 明确限制，不承诺等同能力

### 5.4 预期成果

- Windows 形成成熟主力版本
- macOS 达到基础可用并对权限依赖有清晰说明
- Linux X11 达到可用版本并有兼容性边界
- Wayland 有明确降级策略和文档说明

### 5.5 风险点

- 仍然不能把所有平台做成完全一致体验
- 某些深层窗口控制能力仍会受平台政策影响
- Wayland 相关能力可能长期无法达到 Windows 水平

### 5.6 验收标准

- 发布包可稳定运行
- 设置、热键、面板、窗口切换主流程稳定
- 主要平台限制在文档和界面中都有明确提示
- 用户遇到不可用场景时能知道原因和替代方案

## 6. Wayland 专项策略

Wayland 不建议纳入短期版本的强承诺范围，而应作为长期策略项处理。

### 6.1 建议原则

- 不承诺与 Windows 或 X11 等同的能力
- 优先做“检测和说明”，其次才是“兼容探索”
- 若无可靠 portal 或桌面扩展方案，则提供降级体验

### 6.2 建议交付方式

#### 短期

- 检测当前是否为 Wayland
- 在界面中提示限制项
- 禁用不可用功能并说明原因

#### 中期

- 调研 portal
- 调研 GNOME/KDE 环境扩展的可能性

#### 长期

- 如果某些桌面环境提供可依赖能力，再考虑按环境做定向增强

## 7. 资源建议

如果团队资源有限，建议按下面顺序推进：

### 7.1 一人小步快跑模式

适合先做：

1. 搜索
2. MRU 排序
3. 多屏支持
4. 诊断页
5. 配置导入导出

原因：

- 这些功能跨平台一致性较好
- 依赖底层系统接口较少
- 容易形成稳定版本增量

### 7.2 有平台开发能力时

再推进：

1. macOS 热键
2. macOS 关闭窗口
3. Linux X11 热键
4. 图标能力补齐

原因：

- 这些功能需要更深入的平台适配经验

## 9. 总结

这条路线最重要的原则不是“每个平台都做到一样”，而是：

- 先把统一主流程做强
- 再把平台差异讲清楚
- 对能补齐的能力持续补齐
- 对受平台限制的能力明确降级，不做过度承诺

如果按照这个节奏推进，`mySwitcher` 最合适的发展路线是：

- `v0.2`：把体验做强
- `v0.3`：把跨平台主流程补齐
- `v1.0`：把产品稳定性、文档和平台策略做成熟
