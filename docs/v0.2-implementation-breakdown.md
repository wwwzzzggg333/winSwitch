# mySwitcher v0.2 开发任务拆解

## 1. 版本目标

`v0.2` 的目标是提升窗口切换主流程的效率和可解释性，在不扩大高风险平台范围的前提下，补齐最有收益的共性能力。

本版本重点不是补齐所有平台底层能力，而是围绕以下六个主题形成一个明确可执行的开发范围：

1. 搜索能力
2. 最近使用排序（MRU）
3. 多屏幕感知
4. 热键增强
5. 平台能力诊断页
6. 配置导入导出

## 2. 范围边界

### 2.1 纳入范围

- 搜索能力
- 最近使用排序（MRU）
- 多屏幕感知
- 热键增强
- 平台能力诊断页
- 配置导入导出

### 2.2 不纳入范围

- macOS 全局热键底层实现
- macOS 关闭窗口底层实现
- Linux X11 全局热键底层实现
- Wayland 深度适配
- 更复杂的窗口管理能力
- 大规模视觉改版

### 2.3 执行原则

- 优先做低风险高收益项
- 共性能力优先于平台专项能力
- 平台受限能力必须通过提示和诊断页明示
- 不让高风险底层适配阻塞 `v0.2` 主流程交付

## 4. 任务分组

### A. 搜索能力

- 增加搜索输入状态
- 增加过滤逻辑
- 增加搜索结果展示

### B. MRU 排序

- 记录最近激活时间
- 把 MRU 纳入排序
- 明确 MRU 与置顶规则的优先级

### C. 多屏幕感知

- 增加目标屏幕选择逻辑
- 更新主窗口显示位置策略
- 保留失败回退策略

### D. 热键增强

- 扩充热键录入范围
- 对齐录入与解析能力
- 增强失败提示和平台说明

### E. 平台能力诊断页

- 定义诊断数据结构
- 提供设置页入口或新增视图

- 增加文件选择流程
- 增加 JSON 校验
- 增加导入后的回写和提示

## 5. 任务清单

### 任务 1：搜索能力

目标：

- 支持在切换面板中按标题、应用名、路径实时搜索

主要改动点：

- `src/core/WindowModel.h`
- `src/core/WindowModel.cpp`
- `src/ui/SwitcherPanel.h`
- `src/ui/SwitcherPanel.cpp`
- `src/ui/MainWindow.cpp`

建议实现方向：

- 在状态层增加搜索关键词
- 扩展过滤逻辑
- 在面板顶部加入搜索输入框
- 维持搜索结果中的分组上下文

完成标准：

- 输入关键字后，列表实时收敛到匹配结果
- 搜索支持标题、应用名、路径
- 清空关键字后恢复默认视图

### 任务 2：MRU 排序

目标：

- 记录窗口最近使用时间并把结果体现在窗口顺序中

主要改动点：

- `src/app/Application.cpp`
- `src/core/Config.h`
- `src/core/Config.cpp`
- `src/core/WindowModel.h`
- `src/core/WindowModel.cpp`

建议实现方向：

- 在窗口被激活时写回最近使用状态
- 在构建组和组内窗口时引入最近使用排序
- 明确与置顶规则的默认优先级

完成标准：

- 激活窗口后再次打开面板，组内顺序体现最近使用结果

## 7. 依赖关系

### 7.1 搜索依赖

- 依赖 `WindowModel` 的过滤结构扩展
- UI 层展示依赖搜索状态先定义完成

### 7.2 MRU 依赖

- 依赖窗口激活后状态写回
- 依赖配置或状态结构能承载最近使用信息

### 7.3 多屏幕感知依赖

- 主要依赖 `MainWindow` 的显示位置策略调整
- 与其他模块耦合度相对较低

### 7.4 热键增强依赖

- 依赖 `HotkeyEdit` 和各平台热键解析逻辑的口径统一
- 依赖 i18n 文案补充

### 7.5 诊断页依赖

- 依赖平台能力结构先定义完成
- 依赖 UI 入口设计落定

### 7.6 配置导入导出依赖

- 依赖 `Config` 结构相对稳定
- 依赖设置页交互入口完成

## 8. 建议开发顺序

建议按下面顺序推进：

1. 先扩展 `core/Config` 和 `core/WindowModel` 的数据结构
2. 实现搜索能力
3. 实现 MRU 排序
4. 实现多屏幕感知
5. 实现热键增强
6. 定义平台能力结构并实现诊断页
7. 实现配置导入导出
8. 最后统一补提示文案、交互收尾和回归验证

这样安排的原因：

- 搜索和 MRU 都依赖模型层扩展
- 多屏幕感知相对独立，适合在中段完成
- 诊断页和配置导入导出更适合在前面结构稳定后再接入

## 10. 风险与阻塞项

### 10.1 搜索展示规则风险

搜索与现有分组模型结合后，分组保留程度和展示方式可能需要反复调整。

### 10.2 MRU 与置顶规则冲突风险

如果排序优先级不提前定清，容易导致实现和预期不一致。

### 10.3 诊断页接口过重风险

如果平台能力接口设计得过于复杂，可能反向拖慢 UI 和设置页开发。

### 10.4 热键增强前后端不一致风险

若录入层支持的按键与平台解析层支持不一致，会造成用户设置后无法生效。

### 10.5 平台误解风险

如果平台不支持时没有明确提示，用户仍然会把限制归因于产品 bug。

## 11. 建议完成定义

`v0.2` 拆解文档完成后，应满足以下条件：

- 六个主题的任务边界清晰
- 每个任务都有目标、改动点和完成标准
- 主要影响文件已经识别
- 依赖关系和开发顺序可直接用于排期
- 风险和阻塞项已经前置暴露

满足以上条件后，开发即可基于本拆解进一步拆成 issue、任务卡或实施步骤。
