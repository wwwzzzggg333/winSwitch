# winSwitch 执行型产品方案

## 1. 文档目的

本文档用于定义 `winSwitch` 在 `v0.2` 阶段的执行型产品方案，目标不是做泛化分析，而是给开发和协作方提供一份可直接用于排期、拆任务和验收的规格说明。

本文档重点回答以下问题：

- `v0.2` 要解决什么问题
- `v0.2` 明确做什么、不做什么
- 六个核心主题分别要达到什么效果
- 不同平台下哪些能力属于增强项，哪些能力受系统限制
- 如何判断本阶段交付是否达标

## 2. 背景与现状

`winSwitch` 当前已经具备以下基础能力：

- 托盘常驻
- 单实例运行
- 枚举窗口并按应用分组
- 基础窗口切换
- 关闭单窗口和整组窗口
- 置顶应用与排除应用
- 缩略图和图标的基础展示
- 设置持久化

从当前实现状态看：

- Windows 已接近完整可用
- macOS 属于基础支持
- Linux X11 属于基础支持但主入口不完整
- Linux Wayland 受平台机制限制，很多能力无法作为普通应用直接实现

当前项目的问题不是“完全不可用”，而是“主流程不够高效，跨平台闭环不够完整，可解释性不足”。

## 3. 问题定义

当前版本存在以下核心问题：

### 3.1 主流程效率不足

- 没有关键字搜索，窗口多时定位成本高
- 没有最近使用排序，切换顺序不符合用户真实习惯
- 多屏幕场景下，面板默认居中到主屏幕，操作路径偏长

### 3.2 配置和反馈能力不足

- 热键录入支持范围有限
- 热键注册失败时，提示信息不够系统化
- 用户无法快速判断当前平台支持哪些能力

### 3.3 可迁移性不足

- 缺少配置导入导出能力
- 用户更换设备或需要备份时操作成本较高

### 3.4 平台差异解释不足

- 平台不支持和功能未实现之间的边界不够清晰
- 特别是在 macOS、Linux X11、Wayland 场景中，容易让用户误以为是普通 bug

## 4. 目标与成功标准

本阶段产品目标是：

- 在不引入高风险平台扩张的前提下，显著增强窗口切换主流程体验
- 让 `v0.2` 成为一个低风险、高收益、可直接进入开发执行的增强版本

本阶段成功标准如下：

- 明确 `v0.2` 的范围、边界和非目标
- 明确六个核心主题的行为变化和用户收益
- 明确平台差异与降级策略
- 让开发能够据此直接开始模块拆解和实施
- 让测试和协作方能够基于同一套标准做验收

## 5. 目标用户与使用场景

### 5.1 目标用户

- 高频桌面多任务用户
- 多窗口办公用户
- 多屏幕用户
- 对跨平台桌面工具有连续使用需求的用户

### 5.2 核心使用场景

#### 场景 A：快速切换窗口

用户通过热键打开面板，希望在尽可能少的操作下切到目标窗口。

#### 场景 B：窗口数量较多时快速检索

用户同时打开多个应用和多个窗口，希望通过输入关键字快速定位目标。

#### 场景 C：多屏幕环境就近操作

用户希望面板出现在鼠标所在屏幕，而不是总出现在主屏幕。

#### 场景 D：平台能力可解释

用户在某些平台上遇到热键、缩略图或窗口控制不可用时，希望能知道原因，而不是只能看到无响应。

#### 场景 E：配置备份与迁移

用户希望能导出当前配置，用于迁移、恢复或共享。

## 6. 范围定义

`v0.2` 纳入范围的能力如下：

1. 搜索能力
2. 最近使用排序（MRU）
3. 多屏幕感知
4. 热键增强
5. 平台能力诊断页
6. 配置导入导出

本版本的整体原则是：

- 优先增强跨平台一致性较好的主流程能力
- 不把高风险平台底层实现混入本轮交付承诺
- 把“可解释性”作为和“可用性”同等重要的目标

## 7. 非目标

以下内容明确不属于 `v0.2` 交付承诺：

- macOS 全局热键底层实现
- macOS 关闭窗口底层实现
- Linux X11 全局热键底层实现
- Wayland 深度适配
- 复杂窗口管理能力，如恢复、最小化其他窗口、跨桌面移动等
- 大规模视觉重做或 UI 风格重构
- 云同步、多设备配置中心

这些内容可以作为后续版本的候选项，但不进入 `v0.2` 范围。

## 8. 平台约束与能力分级

为了避免版本目标混乱，本方案把能力分成三层。

### 8.1 共性能力

这类能力应尽量在所有平台上保持一致：

- 搜索
- MRU 排序
- 多屏策略
- 配置导入导出
- 平台能力诊断页

### 8.2 平台增强能力

这类能力依赖平台底层接口，允许平台间存在实现差异：

- 热键底层实现
- 窗口关闭能力
- 缩略图能力
- 图标能力
- 文件管理器路径增强

### 8.3 平台受限能力

这类能力受平台安全模型或系统策略约束，不能作为统一承诺：

- Wayland 下完整全局窗口枚举
- Wayland 下通用全局热键
- Wayland 下跨应用窗口截图
- 某些系统下对任意第三方窗口的精确控制

### 8.4 平台策略

#### Windows

- 维持完整体验
- 优先打磨主流程和易用性

#### macOS

- 明确权限相关缺口
- `v0.2` 仅增强共性能力和提示能力
- 不承诺补齐高风险底层能力

#### Linux X11

- 保留基础支持
- `v0.2` 优先提升共性体验
- 不承诺补齐热键底层实现

#### Wayland

- 明确采用检测、提示、禁用的降级策略
- 不承诺与 Windows 或 X11 等同的窗口控制能力

## 9. 核心功能方案

### 9.1 搜索能力

目标：

- 让用户在切换面板中快速定位窗口

行为定义：

- 在面板顶部增加搜索输入框
- 支持按窗口标题匹配
- 支持按应用名匹配
- 支持按路径匹配
- 输入后结果实时刷新
- 搜索状态下仍保留应用分组信息，避免完全丢失上下文

不做：

- 不做自然语言搜索
- 不做语义检索

用户收益：

- 窗口多时能显著降低查找成本

### 9.2 最近使用排序（MRU）

目标：

- 让排序结果更符合真实使用习惯

行为定义：

- 记录窗口最近激活时间
- 在窗口层面支持按最近使用排序
- 与置顶规则协同

默认口径：

- 组排序优先保持置顶规则
- 组内窗口默认按最近使用排序

用户收益：

- 更接近实际 Alt+Tab 使用习惯

### 9.3 多屏幕感知

目标：

- 让面板显示位置更贴近用户当前操作焦点

行为定义：

- 默认按鼠标所在屏幕显示面板
- 若获取失败则回退到主屏幕
- 结构上为未来支持“跟随前台窗口所在屏幕”预留扩展点

不做：

- 不做跨屏联动面板
- 不做复杂屏幕记忆策略

用户收益：

- 多屏环境下操作路径更短

### 9.4 热键增强

目标：

- 提升热键配置能力和失败可解释性

行为定义：

- 扩大热键录入支持范围
- 尽量对齐录入层与后端解析层的支持范围
- 当热键不可注册或当前平台不支持时，给出明确提示
- 提示文案应明确区分“当前平台不支持”和“当前热键注册失败”

不做：

- 不在 `v0.2` 中承诺补齐 macOS 或 Linux X11 的热键底层实现

用户收益：

- 减少热键配置时的试错成本

### 9.5 平台能力诊断页

目标：

- 让用户和开发快速判断当前环境支持哪些能力

行为定义：

- 展示当前平台
- 展示当前会话类型，如 X11 / Wayland
- 展示热键支持状态
- 展示缩略图能力状态
- 展示图标能力状态
- 展示日志路径

不做：

- 不做复杂性能诊断
- 不做远程上报

用户收益：

- 降低平台误解和排障成本

### 9.6 配置导入导出

目标：

- 提高配置迁移与备份效率

行为定义：

- 支持导出当前配置到 JSON 文件
- 支持从 JSON 文件导入配置
- 导入时做基础格式校验
- 导入失败时给出明确错误提示

不做：

- 不做云同步
- 不做多设备配置中心

用户收益：

- 方便迁移、备份和恢复设置

## 10. v0.2 范围说明

`v0.2` 的核心定位是“体验增强版”，重点是让主流程明显更好用，而不是补齐所有平台底层能力。

本版本收敛原则如下：

- 优先共性能力
- 只做低风险高收益项
- 对平台限制明确降级
- 不因为个别平台高风险能力而拖慢整体版本推进

换句话说，`v0.2` 要达成的是：

- 搜索更快
- 排序更合理
- 多屏更顺手
- 热键反馈更清楚
- 平台能力更透明
- 配置迁移更方便

## 11. 验收标准

`v0.2` 规格定义完成后，后续实现应至少达到以下结果：

- 用户可在面板中输入关键字搜索窗口
- 搜索支持标题、应用名、路径三个维度
- 窗口列表能体现最近使用顺序
- 面板可优先出现在鼠标所在屏幕
- 热键配置失败时能给出明确提示
- 用户可以在界面中查看平台能力状态
- 用户可以导入和导出配置文件

文档层面的验收口径如下：

- 范围和非目标明确
- 六个核心主题的行为定义明确
- 平台限制与降级策略明确
- 可直接作为开发任务拆解的输入

## 12. 风险与降级策略

### 12.1 搜索、分组与 MRU 的协同风险

搜索、分组、置顶、MRU 同时存在时，容易引起展示和排序口径歧义。

策略：

- 先明确默认优先级
- 避免在 `v0.2` 引入过多可切换排序策略

### 12.2 平台理解偏差风险

用户容易把“当前平台不支持”和“程序实现有 bug”混为一谈。

策略：

- 通过诊断页和提示语明确区分
- 对不可用能力采用显式说明，而不是静默失败

### 12.3 范围失控风险

若把 macOS 热键、macOS 关闭窗口、Linux X11 热键、Wayland 适配等高风险项一起纳入，会导致版本发散。

策略：

- 这些能力统一归入后续版本
- `v0.2` 保持共性体验优先

### 12.4 Wayland 相关风险

Wayland 下很多能力受平台安全模型限制，不存在简单的一次性补齐方案。

策略：

- 继续采用检测、禁用、说明的降级模式
- 不对 Wayland 承诺与 Windows 或 X11 同级的能力

## 13. 总结

本方案的核心不是追求所有平台同一时间达到同一深度，而是：

- 先把统一主流程做强
- 再逐步补平台差异
- 对可做的能力持续增强
- 对受限能力明确说明和降级

按照这个原则，`v0.2` 应被视为一个明确聚焦、可直接进入开发实施的体验增强版本。
