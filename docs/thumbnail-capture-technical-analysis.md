# mySwitcher 缩略图抓取技术分析

## 1. 背景与问题现象

`mySwitcher` 当前在 Windows 下通过 `PrintWindow` 抓取窗口缩略图。

从实际使用现象看，已经出现以下典型问题：

- 有些窗口只能截到标题栏
- 有些窗口只能截到顶部一部分
- 有些窗口缩略图是纯黑或纯白
- 有些窗口缩略图为空
- 同一个窗口在不同状态下可能表现不一致

这些现象并不都来自同一个原因。它们通常由两类因素叠加造成：

- 当前实现策略本身存在风险
- Windows API 以及具体应用窗口类型存在天然限制

因此，这个问题不能简单归结为“截图代码坏了”，也不能反过来认为“都是平台限制，无需优化”。更准确的判断是：

- 一部分问题值得优先修正
- 一部分问题即使修正当前实现，也不能保证完全消失

## 2. 当前实现路径

当前 Windows 缩略图抓取逻辑位于 `src/platform/windows/WinWindowSource.cpp`，核心实现是 `WinThumbnailCapture::capture()`。

主要流程如下：

1. 使用 `GetClientRect()` 获取窗口客户区大小
2. 以该尺寸创建兼容位图
3. 调用 `PrintWindow(hwnd, memDc, PW_RENDERFULLCONTENT)` 请求窗口绘制
4. 使用 `GetDIBits()` 读回像素
5. 将 BGRA 转为 RGBA
6. 对纯黑或纯白结果做空白图过滤
7. 最后按固定上限缩放输出

从实现语义上看，当前逻辑默认假设：

- `GetClientRect()` 得到的尺寸适合作为抓图目标尺寸
- `PrintWindow()` 会把需要展示的窗口内容正确绘制到这块位图里

问题恰恰出在这两个假设并不总是成立。

## 3. 为什么会只截到标题栏或截不全

这是当前实现中最值得优先解释的问题。

### 3.1 客户区尺寸与实际绘制范围不一致

`GetClientRect()` 获取的是客户区大小，不包含标题栏和边框。

但 `PrintWindow()` 在很多窗口上并不严格等于“只绘制客户区内容”。在不同窗口实现下，它可能会：

- 绘制整个窗口
- 先绘制非客户区
- 只绘制一部分客户区
- 返回成功但实际内容不完整

如果承接位图只按客户区尺寸创建，而实际绘制范围更接近整窗，就会发生裁切。

### 3.2 为什么会出现“只剩顶部一截”

当绘制内容超出目标位图时，最容易留下的往往是顶部区域。

在可视效果上，这通常表现为：

- 只看到标题栏
- 只看到标题栏加顶部少量内容
- 整个图像像是从上方被截下来的一条

这类现象非常符合“承接位图尺寸偏小，但绘制语义偏整窗”的结果。

### 3.3 这属于什么性质的问题

这类问题首先属于当前实现策略存在明显风险：

- 使用客户区尺寸去承接 `PrintWindow()` 的输出，本身就不稳定

同时它也叠加了 API 行为不一致的问题：

- 不同应用对 `PrintWindow()` 的响应并不统一

换句话说：

- “只截到标题栏”并不只是偶发 bug
- 它和当前尺寸选择策略高度相关

## 4. 为什么有些窗口完全截不到

并不是所有窗口都适合通过 `PrintWindow` 稳定抓取。

以下类型的窗口更容易失败：

- Electron / Chromium 窗口
- GPU 硬件加速窗口
- DirectX / OpenGL 渲染窗口
- 最小化窗口
- 被遮挡或后台状态特殊的窗口
- 高权限或受保护窗口
- 某些现代 UI 框架窗口

在这些场景下，即使 `PrintWindow()` 返回成功，也可能出现：

- 纯黑图
- 纯白图
- 空图
- 只绘出边框或标题栏
- 绘出过期内容

这说明“抓不到”并不总是实现写错。很多时候是 API 与应用窗口实现之间天然不稳定。

### 4.1 为什么现代窗口更容易失败

一些现代桌面应用并不是按传统 GDI 语义输出窗口内容，而是依赖：

- GPU 合成
- 离屏缓冲
- 浏览器内核绘制
- 自定义窗口框架

这类窗口即使在屏幕上显示正常，也不代表 `PrintWindow()` 能拿到完整内容。

### 4.2 为什么窗口状态也会影响结果

某些窗口在不同状态下会出现不同抓图结果，例如：

- 前台时能抓到，后台时抓不到
- 普通显示时能抓到，最小化后抓不到
- 未遮挡时能抓到，被覆盖后结果异常

这说明窗口可见性、合成策略和应用自身实现都会影响抓取稳定性。

## 5. 当前实现的具体风险点

当前实现至少存在以下风险点：

### 5.1 尺寸来源风险

当前使用 `GetClientRect()` 作为抓图尺寸来源。

这是最直接的风险点，因为它默认抓的是客户区语义，但 `PrintWindow()` 并不保证只输出客户区内容。

### 5.2 `PrintWindow` 成功不等于内容完整

即使 `PrintWindow()` 返回成功，仍可能出现：

- 内容缺失
- 只画出一部分
- 只有顶部或边框
- 画面为空

因此，“调用成功”不能视为“抓图成功”。

### 5.3 当前空白图识别过于粗糙

当前逻辑只过滤纯黑或纯白图。

这能拦住最明显的失败结果，但识别不了以下情况：

- 半截图
- 只有标题栏的图
- 只画出边框的图
- 颜色正常但内容错误的图

也就是说，当前实现已经能过滤“完全空”，但还过滤不了“明显不对但不空”的结果。

### 5.4 没有按窗口类型做降级

当前逻辑对所有窗口一视同仁，抓失败后基本就是返回空图。

这会导致：

- 某些天然不稳定的窗口体验较差
- 系统没有区分“可优化失败”和“天然高风险失败”

### 5.5 没有后备抓图路径

当前实现基本依赖 `PrintWindow()` 这一条主路径。

一旦该路径对某类窗口不可靠，就没有额外兜底，只能退为空图。

## 6. 可选改进方向

后续如果要优化，可以优先考虑以下方向。

### 6.1 先修正尺寸语义

这是最值得优先尝试的方向。

建议先评估：

- 用整窗尺寸而不是客户区尺寸承接绘制
- 对比 `GetWindowRect()` 与 `DWMWA_EXTENDED_FRAME_BOUNDS`

这一步不能保证解决所有失败，但很可能直接改善“只截到标题栏”或“只截到顶部一部分”的问题。

### 6.2 明确目标到底是“整窗”还是“客户区”

当前实现实际上没有把这个语义定义清楚。

后续需要先明确：

- 产品上想展示的是用户看到的整个窗口
- 还是只想展示窗口内容区

只有先把目标定义清楚，才能决定：

- 应该用什么矩形作为承接尺寸
- 应该允许标题栏出现还是不允许出现

### 6.3 对失败窗口做降级

不是所有窗口都值得强行抓完整缩略图。

更现实的策略是：

- 对稳定可抓的窗口展示缩略图
- 对高风险窗口降级为图标 + 标题

这样可以避免把明显错误的半截图继续展示给用户。

### 6.4 区分“可优化问题”和“不可保证问题”

后续实现时，建议明确把问题分成两类：

- 可优化问题：例如尺寸语义错误、降级策略缺失
- 不可保证问题：例如某些现代窗口类型对 `PrintWindow()` 本身就不稳定

这种区分很重要，因为它直接决定：

- 哪些问题适合投入开发修复
- 哪些问题只能通过说明和降级处理

## 7. 不应误判为普通 bug 的场景

以下场景不应简单归类为“普通实现 bug”：

- 某些窗口即使修正当前尺寸策略后，仍然抓不到完整内容
- 某些应用类型天然就不稳定
- 某些窗口在最小化、后台、被遮挡或高权限状态下失败

这些问题更多属于平台能力边界，而不是单纯代码缺陷。

更具体地说：

- 如果问题稳定发生在某一类现代 GPU 合成窗口上，不能轻易承诺“改一下就彻底解决”
- 如果问题来自当前尺寸策略与绘制语义不匹配，则属于明确值得优化的实现问题

## 8. 结论

当前缩略图问题可以归纳为两大类。

第一类是实现策略问题：

- 当前使用 `GetClientRect()` 配合 `PrintWindow()`，很容易产生绘制范围与位图尺寸不一致的问题
- 这类问题最容易表现为只截到标题栏或顶部一部分

第二类是平台与窗口类型限制：

- 某些窗口天然不适合通过 `PrintWindow()` 稳定抓取
- 即使调用成功，也可能拿不到完整内容

因此，后续如果要优化，最合理的优先顺序是：

1. 先修正尺寸语义问题
2. 再完善失败降级策略
3. 接受一部分窗口类型天然不可保证完全稳定

一句话总结：

- “只截到标题栏”或“只截到顶部一部分”最值得优先从当前实现策略上修正
- “完全抓不到”则需要接受一部分属于 Windows API 和窗口类型的天然限制
